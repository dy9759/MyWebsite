## 一句话
语音产品的体验不由“识别率”单独决定，而由一连串小决策决定：什么时候确认、听不清怎么办、谁先说话、停顿多久算说完、等待时说什么。这本书把这些决策逐一拆开，给出可以直接落地的默认值和反例。

## 核心框架
- **对话超过一轮**：书里的“对话式设计”指的是跨轮次思考——记住上下文、预判用户下一步，但让用户决定对话多长。
- **确认要按风险分级**：错误代价高就显式确认，低就隐式确认或直接执行；能用屏幕、灯光、提示音、动作本身确认的，就不必开口。
- **错误是常态**：没听到、听到但没识别、识别对了却处理错、识别错了，四类错误分别设计；逐级升级的提示、换输入方式、转人工，是兜底链路。
- **轮次与时间是一等公民**：插话（barge-in）、唤醒词、句尾判停超时、无语音超时、延迟提示，这些“时间参数”直接决定对话是否顺畅。
- **上线才是开始**：先定义任务完成率等成功标准，把识别结果、N-best、音频、超时、打断位置都记日志，再用真实数据调置信度阈值和超时。

## 章节笔记

<!-- chapter: 1. Introduction -->
### 引言（Introduction）
- 语音交互经历了两代：电话 IVR 是第一代，手机助手和智能音箱是第二代；作者认为第二代设计者正在重新踩 IVR 时代早已踩过的坑。
- 语音的优势是快、免手、直觉、能传达语气；劣势在公共场合、隐私话题、不愿对机器说话的人群。
- 是否加语音入口，要看用户场景是否真的需要（做饭、开车、情绪脆弱时），而不是因为时髦。
- 原文：「Adding a VUI because it’s cool and trendy is not the right path.」
- 怎么用：立项时我先写清“为什么这一步非用语音不可”，写不出来就把语音降级为可选入口。

<!-- chapter: 2. Basic Voice User Interface Design Principles -->
### 语音交互设计基本原则（Basic Voice User Interface Design Principles）
- 设计工具从“样例对话”开始：挑最常见的五个场景写最佳路径，再写几段出错路径，并且一定要念出来、两人对读。
- 确认策略有五种：三档置信度（高则隐式、中则显式、低则重问）、纯隐式、非语音确认（动作本身/提示音）、泛化确认（“嗯，明白”）、屏幕确认。选哪种取决于出错代价和可用的反馈通道。
- 错误处理：没听到时，能用按钮或画面继续的场景可以“什么都不做”，让用户自然重说；需要回答才能继续时再明确提示，并逐级给出更具体的帮助，多次失败后换输入方式或转人工；永远不要把错误归咎于用户。
- 轮次：说明在前、问题在后，否则用户听到问题就开口，和后半句撞车；不要问自己听不懂答案的反问句。
- 延迟：预知会慢就提前告诉用户并配合提示音或动画；说了“请稍等”就别马上接话，否则听起来像坏了。
- 原文：「When at all possible, do not blame the user.」
- 原文：「If you set up the expectation of a delay, do not violate that expectation.」
- 怎么用：我把“出错代价 × 可用反馈通道”做成一张表，每个需要确认的意图都在表里落位，而不是统一一句“您是说……对吗？”。

<!-- chapter: 3. Personas, Avatars, Actors, and Video Games -->
### 人设、虚拟形象、演员与游戏（Personas, Avatars, Actors, and Video Games）
- 没有“没有个性”的语音界面：用户一定会拟人化，所以人设要主动设计，包括如何回应粗鲁和骚扰、是否承认自己是机器。
- 人设要一致；只换声音或形象不换整套说话方式，会造成违和与不信任。
- 有形象或视频时，“继续注视、偶尔点头”的主动倾听就是最好的“没听清”提示，用户会自然重说。
- 视频类对话通常关闭插话，但必须在角色说完的那一刻立即开麦，并给出明确的“轮到你了”视觉提示，否则开头一两秒丢失就容易误识别。
- 原文：「The best strategy is to decide on the personality yourself, while designing, rather than leave it up to chance.」
- 原文：「Fine-tuning the point at which a user can begin speaking, however, is crucial.」
- 怎么用：我会把“开麦时刻”和“轮到用户说话的信号”写进交互规格，作为单独验收项，而不是交给默认实现。

<!-- chapter: 4. Speech Recognition Technology -->
### 语音识别技术（Speech Recognition Technology）
- 选引擎看两点：识别准确率，以及常被忽视的句尾检测（endpoint detection）。
- 插话：IVR 默认允许任何声音打断；音箱用唤醒词式“热词打断”，避免旁人说话或打喷嚏中断播报；带插话的提示语里不要留停顿，否则会出现互相抢话又同时闭嘴的尴尬。
- 三种超时：句尾超时（约 1.5 秒起步，按状态调：是/否可短，开放式描述、念卡号要长）；无语音超时（约 10 秒，与句尾超时分开统计）；说太久超时（少用）。
- 无语音时别说“请大声点”，而是给出路径：告诉用户信息在哪找、允许说“我不知道”、换个方式继续。
- N-best 列表：首选不匹配就往下找；用户否认过的候选放进跳过列表，避免反复问“是 Austin 吗？”。
- 原文：「Often, people become so caught up in focusing on an ASR tool’s accuracy that they forget about the second crucial requirement: good endpoint detection.」
- 原文：「A pause of 1.5 seconds is a good rule of thumb for most types of VUI responses.」
- 怎么用：我会把判停阈值按对话状态配置，而不是全局一个值；“被截断”和“等太久”两类投诉分别对应调短和调长。
- 我的看法（非书中观点）：今天的端到端实时语音模型普遍用语义判停和流式全双工，固定秒数的超时不再是唯一手段，但“按状态区分判停策略、截断比慢更伤人”这一原则依然成立，只是参数从秒数变成了模型的判停置信度。

<!-- chapter: 5. Advanced Voice User Interface Design -->
### 进阶语音交互设计（Advanced Voice User Interface Design）
- 作者判断：识别准确率提升后，难点从“听清”转移到“听懂”（NLU）。
- 输入处理由浅入深：受限回答（是/否、颜色列表）、开放式回应（不需要精确处理时给通用回应，或告知会转给医生等第三方）、按类别归并、通配符与逻辑表达式、意图加对象。
- 消歧三种情况：信息不足（哪个 Springfield？）、信息过多（同时报两个症状，就请用户先选最困扰的一个，并记住另一个）、否定（“要蘑菇不要辣肠”被识别成两样都要）。
- 对话管理用“槽位”：允许用户一次说全，也允许一点点给，跟着用户的节奏补问。
- 是否把识别文本显示给用户：搜索类需要显示以便纠错；闲聊类显示错字反而损害信任。
- 情绪识别要保守：不要直接说出用户的情绪，只用它来调整对话走向。唤醒词应在本地处理。
- 原文：「Follow your user’s lead, and be prepared to handle information in a variety of ways.」
- 原文：「Handling these takes more work, but the cost of ignoring them can be high.」
- 怎么用：我会为每个关键意图准备“否定”和“多信息”两类测试句，作为上线前必过用例。

<!-- chapter: 6. User Testing for Voice User Interfaces -->
### 语音交互的用户测试（User Testing for Voice User Interfaces）
- 测试时先不告诉用户“可以说话”，观察他们能否自己发现何时、怎样开口。
- 早期低成本方法：样例对话对读、和开发一起对读以暴露实现难点、绿野仙踪（WOz）测试——由人在幕后扮演系统，可用文字聊天模拟，或故意“一律出错”来测试兜底路径。
- WOz 与真实系统的最大差别是识别准确率：扮演者要保守判断“这句话系统真的能处理吗”。
- 观察重点：用户是否知道何时能说话、哪里犹豫、任务时长；主观与客观指标都要收集，因为“失败但不在意”和“成功但不满意”都存在。
- 原文：「Testing with real users, early and often, is crucial.」
- 原文：「Tracking the number and type of errors is very important in a VUI system.」
- 怎么用：我做测试记录时把“拒识”和“错识”分开计数，并记录每次出错后用户是否恢复、花了多久。

<!-- chapter: 7. Your Voice User Interface Is Finished! Now What? -->
### 上线之后（Your Voice User Interface Is Finished! Now What?）
- 上线前做“对话遍历测试”：每个状态都要走到，每个状态下都要试出界说法、沉默、连续多次出错。
- 成功标准要在上线前和业务方一起定，而且不能只看识别率；任务完成要合理切分（查余额和付款应是两个任务）。
- 要追踪的指标：任务完成率、流失点、用户在哪里沉默、在哪里打断（新手和老手分开看）、语音与触屏的使用比例、识别延迟、整通对话回放。
- 日志从第一天就要设计：识别结果与置信度、N-best、每轮音频、匹配结果、各类超时与错误、状态名。
- 调优对象：每个状态的置信度阈值、句尾超时、是否用中间结果抢答（是/否状态可以，列表类会截断用户）、自定义词表。
- 原文：「Too often success is measured solely in terms of recognition accuracy.」
- 原文：「If your latency is too high, users will not think that they’ve been heard and will repeat themselves, which can cause problems.」
- 怎么用：我会把“延迟过高 → 用户重复 → 重复语音被当成新输入”当成一条明确的故障链路去监控，而不只是看平均延迟。

<!-- chapter: 8. Voice-Enabled Devices and Cars -->
### 语音设备与汽车（Voice-Enabled Devices and Cars）
- 智能音箱的成功一半来自麦克风阵列和远场信号处理；人设要匹配使用场景，可爱的性格未必适合给医疗建议。
- 车载语音的难点：噪声、升级周期慢、按键不统一、驾驶本身的认知负荷。把 28 条命令一次念给司机是典型反例。
- 车内应只做最核心的任务，并用预设捷径降低记忆负担；尽量不依赖屏幕，帮助司机抵抗看手机的诱惑。
- 原文：「Interactions in the car should be as simple and easy to remember as possible.」
- 怎么用：凡是“用户双手和视线被占用”的场景，我都按车载标准评审：命令要少、反馈要靠声音、能不看屏幕就完成。

## 读完留下
**听、说、对话交互检查表**

确认
- [ ] 每个意图标注出错代价（高/中/低），对应显式确认、隐式确认或直接执行
- [ ] 置信度分三档，阈值按状态单独设定，并有上线后回调计划
- [ ] 能用动作结果、提示音、灯光或屏幕确认的，不再用语音重复
- [ ] 隐式确认后保留撤销/返回一步的能力
- [ ] 退出、挂断、支付等不可逆操作在中等置信度时必须二次确认

错误恢复
- [ ] 四类错误（无语音、无识别、识别对但处理错、识别错）各有对应策略
- [ ] 提示逐级升级：重问 → 给出具体帮助（在哪找、长什么样）→ 换输入方式 / 转人工
- [ ] 提供“我不知道”之类的出口，而不是原句重复
- [ ] 用 N-best 回退，用户否认过的候选不再重复提议
- [ ] 错误提示不责怪用户；否定句、多信息回答、“是/否”回答开放选择题都有测试用例

轮次与打断
- [ ] 明确每个状态是否允许插话；播报长内容时用热词打断而非任意声音打断
- [ ] 提示语“说明在前、问题在后”，问题之后不再追加内容，提示中不留会被误判为轮次结束的停顿
- [ ] 系统说完立即开麦，且有清晰的“轮到你了”信号
- [ ] 唤醒后的收听窗口有明确时长；唤醒词本地处理
- [ ] 支持“帮助 / 我在哪 / 重复 / 返回 / 再见”这类通用指令

时间与延迟
- [ ] 句尾判停按状态配置：是/否短，开放式描述和念数字串长
- [ ] 无语音超时与句尾超时分开配置、分开统计
- [ ] 已知的慢操作提前告知，并配合提示音或动画；说了“稍等”就真的稍等
- [ ] 监控识别延迟，以及“延迟导致用户重复说”的发生率
- [ ] 中间结果抢答只用于简单状态

上线后
- [ ] 上线前定义任务完成标准与流失点统计口径
- [ ] 日志包含识别文本、置信度、N-best、音频、超时类型、状态名、打断位置
- [ ] 定期抽样回放整段对话，覆盖不同时段与星期

## 我的问题清单
- 实时全双工语音模型允许用户随时插话、系统也能边听边说，书中“关闭插话 + 精确开麦”的做法，什么场景下仍然更稳妥？（我的看法：需要严格结构化输入的场景，比如念号码、确认支付，可能仍然更适合半双工。）
- 用语义判停替代固定秒数之后，“被截断”和“等太久”的权衡该用什么指标在线衡量？
- 当大模型几乎什么都能接住时，“诚实告知能力边界、不要过度承诺”如何体现在开场和帮助提示里？
- 三档置信度确认在端到端模型里拿不到可靠的置信分时，用什么信号替代？
