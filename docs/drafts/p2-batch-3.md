## 1. 边界条件 `edge-case`
- **EN**: Edge Case ｜ **归类**: AI · 上下文 ｜ **来源**: 第2章·上下文工程与 spec 写作
- **tagline**: 输入的极端与异常情形：空的、超长的、重复的、并发的——bug 最爱住的地方。
- **hook**: 正常流程都对了，为什么一上线还是炸？
- **description**: 常规路径只是需求的一半；列表为空时、字段超长时、用户连点两次时发生什么，才是专业与业余的分界。给 AI 的 spec 不写边界，它就替你随机决定。
- **✓ 建议**: 每个功能列一遍"空/满/重/并发"四问 ／ 把边界写进 spec 与验收清单 ／ 测试优先覆盖边界而不是重复晴天
- **✗ 避免**: 只按演示数据验证 ／ 假设用户按预期顺序操作 ／ 让 AI 自行"合理处理"异常
- **场景**: 空列表首屏 ／ 超长昵称把布局撑爆 ／ 双击提交产生两笔订单
- **前置**: `spec`

## 2. 约束 `constraints`
- **EN**: Constraints ｜ **归类**: AI · 上下文 ｜ **来源**: 第2章·上下文工程与 spec 写作
- **tagline**: 明确告诉 AI"不能做什么"：技术栈、范围、风格、红线——负空间也是需求。
- **hook**: 为什么 AI 总是顺手换掉你的库、改掉你的样式？
- **description**: AI 缺省会选择"它最熟"的做法；不写约束，它就自由发挥。约束把可行解空间收窄到你要的那一块：只改这个文件、沿用现有组件、不引入新依赖——写清楚，返工减半。
- **✓ 建议**: 任务里写明"只动 X、不碰 Y" ／ 声明技术栈与风格基线 ／ 违反约束一票打回而不是将就
- **✗ 避免**: 只描述目标不划边界 ／ 事后抱怨 AI"自作主张" ／ 约束散落在聊天记录里不进 spec
- **场景**: "不要引入新依赖"的任务前缀 ／ 代码评审里的越界改动 ／ 项目 CLAUDE.md 约定
- **前置**: `spec`

## 3. 范围蔓延 `scope-creep`
- **EN**: Scope Creep ｜ **归类**: 产品 · 产品规划 ｜ **来源**: 第2章·上下文工程与 spec 写作
- **tagline**: 任务边界在执行中不知不觉扩大：顺手加的、随口提的，最后拖垮交付。
- **hook**: 说好的登录功能，怎么做着做着连会员体系都出来了？
- **description**: 人和 AI 都会蔓延：人是"既然都做了不如再加点"，AI 是"顺手帮你重构了"。每次扩一点看似无害，叠加起来交付日期就没了。对抗手段是把范围写死、改动走显式决定。
- **✓ 建议**: spec 里写明"本次不做什么" ／ 新想法记进 backlog 而不是当场做 ／ 每次范围变更显式确认成本
- **✗ 避免**: "顺手把这个也改了" ／ 用蔓延惩罚做得快的人 ／ 把探索和交付混在同一个任务里
- **场景**: PR 里混入无关重构 ／ 需求评审越开越大 ／ AI 交付物里多出没要的功能
- **前置**: `constraints`

## 4. 越界热情 `unsolicited-changes`
- **EN**: Unsolicited Changes ｜ **归类**: AI · Agent 与工具 ｜ **来源**: 第2章·AI 失效模式图鉴
- **tagline**: AI 失效模式之一：没让它改的地方它"好心"改了——顺手重构、顺手换库、顺手美化。
- **hook**: 只让它修一个 bug，diff 里怎么有 40 个文件？
- **description**: 模型倾向"把周围也弄好"，但你没检查的每一处顺手改动都是暗雷：行为悄悄变化、样式全局漂移。验收动作：先看改动清单再看实现，越界一律追问或回滚。
- **✓ 建议**: 每次交付先审 diff 范围 ／ 约束里写明只动指定文件 ／ 越界改动要求 AI 说明理由
- **✗ 避免**: 只看功能能跑就合并 ／ 把顺手改当赚到 ／ 大 diff 懒得看直接过
- **场景**: "顺便重构了一下"的汇报 ／ diff 范围检查 ／ 样式全局被改的事故
- **前置**: `constraints`

## 5. 打转循环 `doom-loop`
- **EN**: Doom Loop ｜ **归类**: AI · Agent 与工具 ｜ **来源**: 第2章·AI 失效模式图鉴
- **tagline**: AI 失效模式之一：同一个问题改来改去修不好，每轮都自信满满，每轮都原地打转。
- **hook**: 第五轮"这次真的修好了"之后，你该怎么办？
- **description**: 连续多轮修不好，说明不是"再试一次"的问题，而是循环方式坏了：上下文里塞满失败尝试，模型在错误方向上越陷越深。破法是打断：清上下文重来、换角度描述问题、或先让它解释根因不许动代码。
- **✓ 建议**: 三轮不中就停下换策略 ／ 让 AI 先讲清根因再改 ／ 新开会话带着干净的问题描述重来
- **✗ 避免**: 无限"再修一下" ／ 情绪化对喷（换来更会道歉的 AI） ／ 在污染的上下文里继续堆指令
- **场景**: 第 N 轮同一个报错 ／ 清空重开后一次修好 ／ "先别改，解释一下"的指令
- **前置**: `context-rot`（本批 #8）

## 6. 过度自信 `overconfidence`
- **EN**: Overconfidence ｜ **归类**: AI · Agent 与工具 ｜ **来源**: 第2章·AI 失效模式图鉴
- **tagline**: AI 失效模式之一：语气的确定程度与内容的正确程度无关——错得也理直气壮。
- **hook**: 它说"已全部测试通过"，你信几成？
- **description**: 模型输出的自信语气是续写出来的风格，不是可信度信号。"已完成""已验证"这类话，除非附带真实运行输出，否则等于没说。验收看证据，不看措辞。
- **✓ 建议**: 要求"跑给我看"——贴真实输出 ／ 把"无证据的完成=未完成"当默认 ／ 对确定语气保持程序性怀疑
- **✗ 避免**: 用语气判断可信度 ／ 接受"应该没问题" ／ 让它自评质量代替验证
- **场景**: "12 个用例全部通过"的口头汇报 ／ 索要测试输出的追问 ／ 上线前的证据清单
- **前置**: `next-token`

## 7. 能跑但错了 `works-but-wrong`
- **EN**: Works-but-wrong ｜ **归类**: AI · Agent 与工具 ｜ **来源**: 第2章·AI 失效模式图鉴
- **tagline**: AI 失效模式之一：演示一切正常，逻辑悄悄错了——最难抓的一类缺陷。
- **hook**: 页面能点、数据能存，为什么月底对账少了钱？
- **description**: 语法对、能运行、演示顺滑，不代表业务正确：金额用了浮点、时区差八小时、状态机漏了分支。这类错测试最难拦，靠的是验收时对"它没做什么"的追问和边界用例。
- **✓ 建议**: 验收用真实业务数据走全流程 ／ 金额、时间、权限三高危区重点查 ／ 让 AI 列出它做过的假设
- **✗ 避免**: 演示通过即上线 ／ 只测晴天路径 ／ 把"能跑"当验收标准
- **场景**: 对账差异排查 ／ 时区显示错乱 ／ 隐藏在正常界面下的错误逻辑
- **前置**: `edge-case`

## 8. 上下文腐烂 `context-rot`
- **EN**: Context Rot ｜ **归类**: AI · 上下文 ｜ **来源**: 第2章·AI 失效模式图鉴
- **tagline**: 长对话里旧信息、失败尝试和互相矛盾的指令淤积，模型表现随之劣化。
- **hook**: 聊得越久越笨，是错觉吗？
- **description**: 上下文是模型的工作台：失败的代码、被否掉的方案、改了三版的口径都躺在上面，它分不清哪些还算数。表现为翻旧账、混淆版本、重复已否决的做法。治理靠主动收纳：总结共识、清场重开。
- **✓ 建议**: 阶段性让 AI 总结"当前有效结论"再继续 ／ 大任务分会话，每段带干净起点 ／ 关键口径写进固定文档而不是靠聊天记忆
- **✗ 避免**: 一个会话从立项聊到上线 ／ 失败尝试不清场继续叠 ／ 指令改口后不声明旧的作废
- **场景**: 长会话后的答非所问 ／ 新开会话立刻变聪明 ／ 会话中期的共识总结
- **前置**: `context-window`

## 9. 仓库 `repository`
- **EN**: Repository / Repo ｜ **归类**: Git · Git ｜ **来源**: 第3章·Git：软件世界的后悔药
- **tagline**: 项目代码与全部版本历史的家：本地一份，远端（如 GitHub）一份副本。
- **hook**: "把仓库拉下来"到底拉的是什么？
- **description**: 仓库不只是当前代码，还包含每一次提交的完整历史。本地仓库让你离线工作与回溯；远端仓库负责备份与协作。删了本地目录，历史随之消失——除非远端还有副本。
- **✓ 建议**: 项目第一天就建仓库 ／ 定期推到远端保平安 ／ 一个产品一个仓库，别散装多处
- **✗ 避免**: 用压缩包命名 v1/v2/final 当版本管理 ／ 只有本地一份历史 ／ 把密钥推进公开仓库
- **场景**: GitHub 仓库首页 ／ git clone 的一瞬间 ／ "删库跑路"段子背后的真实风险
- **前置**: `git`

## 10. 环境 `environment`
- **EN**: Environment ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第3章·环境与部署
- **tagline**: 同一套代码运行的不同世界：本地开发、测试（staging）、生产（用户在用的）。
- **hook**: 为什么不能直接在线上改？
- **description**: 环境隔离是安全网：本地随便折腾，staging 用来彩排，生产只接受验证过的变更。跳过彩排直接改生产，等于在观众面前排练。配置随环境切换（数据库、密钥、开关），代码不变。
- **✓ 建议**: 至少三层：本地 / staging / 生产 ／ 变更先在 staging 全流程走一遍 ／ 环境差异只放配置里
- **✗ 避免**: 直接在生产改代码或数据 ／ staging 与生产配置漂移到面目全非 ／ 本地连生产数据库
- **场景**: staging 域名彩排 ／ 生产事故的"谁直接改了线上" ／ 环境变量按环境注入
- **前置**: `deploy`
- **⚠**: VH 已有 `env-var`（环境变量），本条讲"环境"概念本身，互补不重复。

## 11. On-call `on-call`
- **EN**: On-call ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第3章·环境与部署
- **tagline**: 值守轮班：产品出事时那个电话会响的人——上线不是结束，是开始值班。
- **hook**: 半夜三点报警响了，谁起来看？
- **description**: 有真实用户后，故障不挑时间。On-call 机制明确"现在谁负责"：收到报警、判断影响、止血、事后复盘。单人产品也一样——你自己就是全年无休的 on-call，所以更要靠监控和自动化守夜。
- **✓ 建议**: 报警只留"需要行动"的那几条 ／ 止血优先于找根因 ／ 每次事故写复盘防重演
- **✗ 避免**: 报警泛滥到麻木 ／ 半夜带着起床气改根因 ／ 事故过去就当没发生
- **场景**: 报警群的深夜消息 ／ 事故复盘文档 ／ 假期前的值班交接
- **前置**: `monitoring`

## 12. .env 文件 `dotenv`
- **EN**: dotenv ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第3章·密钥与配置
- **tagline**: 存放密钥与本机配置的小文件；永远不进 git——这是它存在的全部意义。
- **hook**: 史上最贵的一次 git push 是怎么发生的？
- **description**: 代码要进版本库、密钥绝不能进，.env 就是这条边界的实体：程序启动时从中读取配置，.gitignore 保证它不被提交。误推 .env 等于把家门钥匙贴到公告栏——爬虫几分钟内就会扫到。
- **✓ 建议**: 项目初始化第一件事：.env 进 .gitignore ／ 提交 .env.example 说明需要哪些变量 ／ 泄露立即轮换而不是心存侥幸
- **✗ 避免**: 密钥写进代码或配置常量 ／ 把 .env 发到群里 ／ 推错后只删除文件不换密钥（历史里还在）
- **场景**: .gitignore 第一行 ／ 新人拉仓库后的"缺环境变量"报错 ／ GitHub 密钥扫描告警
- **前置**: `config-file`

## 13. 轮换 `key-rotation`
- **EN**: Key Rotation ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第3章·密钥与配置
- **tagline**: 定期或事发后更换密钥，让旧钥匙作废——泄露的唯一正确响应。
- **hook**: 密钥可能泄露了，删掉聊天记录有用吗？
- **description**: 密钥一旦离开受控环境（贴进聊天、推进仓库、进过日志）就当已泄露：撤销旧的、签发新的、更新引用，一气呵成。"应该没人看到"不是安全策略，轮换才是。
- **✓ 建议**: 泄露即轮换，不赌概率 ／ 高价值密钥定期换 ／ 轮换流程写成文档能一键执行
- **✗ 避免**: 泄露后只删消息不换钥匙 ／ 一把密钥用遍所有服务 ／ 轮换后忘了更新部署环境导致宕机
- **场景**: 控制台的 Regenerate Key 按钮 ／ 泄露响应 SOP ／ 轮换后的服务重启
- **前置**: `dotenv`

## 14. 认证 `authn`
- **EN**: Authentication (AuthN) ｜ **归类**: 后端 · 账号与权限 ｜ **来源**: 第4章·认证与授权
- **tagline**: 确认"你是谁"：登录、验证码、token——进门前先验明正身。
- **hook**: 登录了就安全了吗？那只回答了一半问题。
- **description**: 认证解决身份问题：密码、短信码、第三方登录都是手段，产出通常是一张会过期的凭证（token/session）。它只保证"你是你"，至于"你能做什么"，是授权的事——这两个词差一个字，差一类事故。
- **✓ 建议**: 用成熟登录方案而不是自造 ／ 凭证设过期与刷新 ／ 敏感操作要求二次确认
- **✗ 避免**: 密码明文存储 ／ 凭证永不过期 ／ 把"已登录"当"有权限"
- **场景**: 登录页与验证码 ／ token 过期后的重新登录 ／ 密码加盐哈希的存储
- **前置**: `authentication`（VH 原有条目为组件视角，本条为课程安全视角——审校时定并存或合并）

## 15. 授权 `authz`
- **EN**: Authorization (AuthZ) ｜ **归类**: 后端 · 账号与权限 ｜ **来源**: 第4章·认证与授权
- **tagline**: 确认"你能做什么"：这条数据是不是你的、这个操作你够不够格。
- **hook**: 用户 A 换个 id 就能看用户 B 的订单——问题出在哪？
- **description**: 授权检查必须发生在服务端的每一次数据访问上：不只验证登录，还要验证归属与角色。漏掉授权就是越权事故（IDOR）：接口能跑、演示正常，换个参数就是别人的数据。
- **✓ 建议**: 每个接口问一句"这条数据是他的吗" ／ 角色权限集中定义 ／ 用他人 id 实测越权
- **✗ 避免**: 只靠前端隐藏按钮当权限 ／ 查询不带归属条件 ／ 管理接口裸奔上线
- **场景**: 改 URL id 的越权测试 ／ 权限矩阵评审 ／ "客服可见全部"的角色设计
- **前置**: `authn`
