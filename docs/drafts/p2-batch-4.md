## 1. IDOR / 越权 `idor`
- **EN**: Insecure Direct Object Reference ｜ **归类**: 后端 · 账号与权限 ｜ **来源**: 第4章·认证与授权
- **tagline**: 最常见的越权漏洞：把 URL 或参数里的 id 换成别人的，就能看到别人的数据。
- **hook**: 订单页地址是 /orders/1024，改成 1023 会发生什么？
- **description**: 接口收到 id 就直接查库返回，忘了问一句「这条数据属于当前用户吗」——这就是 IDOR。它不需要任何黑客技术，改个数字就能复现，却常年霸榜真实事故清单。防法只有一个：服务端每次访问都校验归属。
- **✓ 建议**: 每个带 id 的接口都加归属校验 ／ 上线前用他人 id 手动实测一轮 ／ 敏感资源用不可猜的 id（如随机串）作辅助
- **✗ 避免**: 相信「用户不会去改 URL」 ／ 只在列表页过滤、详情页裸查 ／ 把不可猜 id 当唯一防线（辅助不是替代）
- **场景**: 改 URL 数字看到别人订单 ／ 渗透测试报告高频项 ／ 「越权访问」事故通报
- **前置**: `authz`

## 2. 脱敏 `data-masking`
- **EN**: Data Masking ｜ **归类**: 后端 · 账号与权限 ｜ **来源**: 第4章·认证与授权
- **tagline**: 敏感数据展示前先打码：手机号中间四位、身份证只留尾号——能少给就少给。
- **hook**: 客服系统为什么显示 138****1234，而不是完整手机号？
- **description**: 不是所有看到这条数据的人都需要看到全部字段。脱敏在返回和展示层把敏感信息削到「够用为止」：客服核对身份看尾号就够，导出报表根本不该带身份证。原则是最小披露——泄露时损失也跟着最小。
- **✓ 建议**: 接口按角色返回字段而不是一律全量 ／ 日志与报表默认脱敏 ／ 明确哪些字段属于敏感清单
- **✗ 避免**: 前端打码、接口照传全文（抓包全裸） ／ 把完整敏感数据打进日志 ／ 「内部系统不用脱敏」的侥幸
- **场景**: 客服后台的打码手机号 ／ 抓包看到接口返回全文的翻车现场 ／ 数据导出评审
- **前置**: `authz`

## 3. 软删除 `soft-delete`
- **EN**: Soft Delete ｜ **归类**: 后端 · 数据库 ｜ **来源**: 第4章·认证与授权
- **tagline**: 删除不真删：打个「已删除」标记藏起来，数据还在，随时能恢复、能对账。
- **hook**: 用户手滑删掉的东西，你的产品能找回来吗？
- **description**: 真删（物理删除）是不可逆操作：误删、bug 删、被攻击删，都没有后悔药。软删除给记录加一个 deleted 标记，查询时过滤掉——用户看是删了，数据库里还留着底。代价是所有查询都要记得带过滤条件，且敏感数据该真删时要真删（合规要求）。
- **✓ 建议**: 用户数据默认软删除 ／ 查询统一封装过滤逻辑，别每处手写 ／ 定期清理与合规删除并行设计
- **✗ 避免**: 让 AI 生成的 DELETE 语句直接跑生产 ／ 软删了但某个查询忘了过滤（「已删除」数据诈尸） ／ 用软删除逃避合规的真删义务
- **场景**: 回收站功能 ／ 误删恢复工单 ／ 「删除的数据怎么还出现在列表里」的 bug
- **前置**: `database`

## 4. 注入攻击 `injection`
- **EN**: Injection ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第4章·输入与数据安全
- **tagline**: 把「数据」伪装成「指令」塞进系统：输入框里写一段 SQL，数据库就照做了。
- **hook**: 用户名填 `'; DROP TABLE users;--` 会发生什么？
- **description**: 程序把用户输入直接拼进 SQL、命令或模板里执行，攻击者就能让输入「越狱」成指令——这就是注入，二十年来始终排在漏洞榜前列。根治不靠过滤黑名单，靠让数据永远走数据通道：参数化查询、预编译语句。
- **✓ 建议**: 数据库操作一律参数化查询 ／ 用 ORM 等成熟库而不是手拼 SQL ／ 对 AI 生成的裸拼接字符串保持警觉
- **✗ 避免**: 字符串拼接构造 SQL ／ 靠「过滤敏感词」防注入 ／ 相信「内部接口没人攻击」
- **场景**: 登录框注入试探 ／ 代码评审揪出的拼接 SQL ／ 安全扫描报告
- **前置**: `input-validation`（本批 #6）

## 5. XSS `xss`
- **EN**: Cross-Site Scripting ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第4章·输入与数据安全
- **tagline**: 注入的浏览器版：把脚本混进用户输入，谁打开页面就在谁的浏览器里执行。
- **hook**: 评论区发一条「评论」，为什么能偷走所有看到它的人的登录态？
- **description**: 用户输入未经处理直接渲染进页面，输入里的 `<script>` 就成了页面的一部分——在每个访问者的浏览器里运行，能偷 cookie、改页面、冒充操作。防线是输出转义：内容显示为文本，永远不当代码执行。
- **✓ 建议**: 渲染用户内容一律转义（现代框架默认就有，别绕过） ／ 富文本用白名单过滤库 ／ 关键 cookie 设 HttpOnly
- **✗ 避免**: 直接把用户输入塞进 innerHTML ／ 为了「支持 HTML」关掉框架的默认转义 ／ 只防表单、忘了 URL 参数也是输入
- **场景**: 评论区弹窗恶作剧 ／ 富文本编辑器的过滤方案评审 ／ 框架里 dangerouslySetInnerHTML 的命名警告
- **前置**: `injection`

## 6. 输入校验 `input-validation`
- **EN**: Input Validation ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第4章·输入与数据安全
- **tagline**: 安全第一定律：永远不要相信任何外部输入——前端拦的是失误，服务端拦的才是攻击。
- **hook**: 前端已经做了校验，服务端为什么还要再做一遍？
- **description**: 前端校验是用户体验：即时提示、少跑一趟。但攻击者不经过你的前端——直接调接口，什么都能传。服务端校验才是安全边界：类型、长度、范围、格式，一样不少地再查一遍。两层各干各的活，谁也替代不了谁。
- **✓ 建议**: 服务端把每个入参当敌意输入检查 ／ 校验规则集中定义、两端复用 ／ 拒绝时返回明确错误而不是静默吞掉
- **✗ 避免**: 「前端已经拦了」就跳过服务端校验 ／ 只校验必填、不校验范围与格式 ／ 对内部服务来的数据盲目信任
- **场景**: 绕过前端直接 curl 调接口 ／ 负数金额下单的经典漏洞 ／ 接口参数规则评审
- **前置**: `data-validation`
- **⚠**: VH 已有 `data-validation`（数据校验，表单/接口视角），本条讲「不信任外部输入」的安全律，互补并挂它为前置。

## 7. 转义 / 参数化 `escaping`
- **EN**: Escaping / Parameterized Query ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第4章·输入与数据安全
- **tagline**: 防注入的两件正装：转义让数据显示成文本，参数化让数据永远进不了指令通道。
- **hook**: 同样是处理危险输入，「洗干净」和「分开走」有什么区别？
- **description**: 转义是把特殊字符变成无害写法（`<` 变 `&lt;`），内容再刁钻也只是文本；参数化是查询语句和数据分两条通道送进数据库，数据无论长什么样都只是值。两者共同点：不靠猜测「哪些输入危险」，而是从结构上让危险不可能发生。
- **✓ 建议**: 输出到页面→转义；进数据库→参数化，各就各位 ／ 用框架与库的内置机制 ／ 评审时看结构（拼没拼）而不是看过滤列表全不全
- **✗ 避免**: 自己写正则「过滤危险字符」 ／ 转义一次就以为处处安全（场景不同转义规则不同） ／ 部分参数化、部分拼接的混合体
- **场景**: ORM 的占位符写法 ／ 模板引擎的自动转义 ／ 安全评审的「有没有拼接」一问
- **前置**: `injection`

## 8. 文件上传风险 `upload-risk`
- **EN**: Upload Risk ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第4章·输入与数据安全
- **tagline**: 上传的不只是文件，可能是伪装的可执行代码：改个扩展名，头像变后门。
- **hook**: 用户上传的「图片」，为什么可能让服务器沦陷？
- **description**: 上传接口是把外部文件请进家门。只看扩展名等于看名片认人：把脚本改名 .jpg 一样传得进来；如果存储位置还允许执行，攻击者就有了自己的后门。防法是层层设防——校验真实类型、重命名、限制大小、存到不可执行的位置。
- **✓ 建议**: 按文件内容（魔数）识别类型而不是扩展名 ／ 上传后重命名并存对象存储/静态目录 ／ 限制大小与频率
- **✗ 避免**: 只校验扩展名 ／ 用户文件存进代码目录 ／ 上传目录开执行权限
- **场景**: 头像上传接口评审 ／ webshell 攻击案例 ／ 对象存储的默认防执行设计
- **前置**: `upload` `input-validation`
- **⚠**: VH 已有 `upload`（上传组件，交互视角），本条讲服务端风险，挂它为前置。

## 9. 验收 `acceptance`
- **EN**: Acceptance ｜ **归类**: 技术栈 · 测试 ｜ **来源**: 第4章·验收思维
- **tagline**: AI 时代产品人的核心手艺：不会写代码没关系，会判断「这个能不能收」才是关键。
- **hook**: 代码是 AI 写的，出了事算谁的？
- **description**: 写代码可以外包给 AI，收货责任外包不掉。验收不是「点两下没报错」，而是一套动作：对照 spec 核对做没做全、走异常路径、查改动范围、要运行证据。你签收的那一刻，代码的质量就是你的质量。
- **✓ 建议**: 验收对照 spec 逐条打勾 ／ 异常路径至少走一遍 ／ 收货前看 diff 范围有没有越界
- **✗ 避免**: 演示顺利就签收 ／ 只验新功能、不管老功能被改坏 ／ 把验收责任推给「AI 说没问题」
- **场景**: 给 AI 交付物做验收的下午 ／ 上线前的最后把关 ／ 事故复盘时的「谁验收的」
- **前置**: `acceptance-criteria`
- **⚠**: VH 已有 `acceptance-criteria`（验收标准，写标准视角），本条讲验收这门实践，挂它为前置。

## 10. 失败路径 `failure-path`
- **EN**: Failure Path ｜ **归类**: 技术栈 · 测试 ｜ **来源**: 第4章·验收思维
- **tagline**: 事情不顺时的每一条岔路：网络断了、余额不够、第三方超时——验收重点全在这。
- **hook**: 支付成功的流程谁都会测，支付到一半断网呢？
- **description**: 晴天路径只有一条，失败路径有无数条：每个外部调用都可能超时，每个输入都可能非法，每一步都可能被用户中途放弃。产品的质感和事故率都藏在失败路径的处理里——报错给不给人话提示、重试会不会重复扣款、中断后状态还对不对。
- **✓ 建议**: 每个流程画出所有失败分支再验收 ／ 断网、超时、重复提交逐个实测 ／ 失败时的提示文案当产品设计做
- **✗ 避免**: 只验成功流程 ／ 失败就白屏或转圈到天荒地老 ／ 假设第三方服务永远在线
- **场景**: 断网测试 ／ 支付中断后的状态排查 ／ 「出错了请重试」的文案评审
- **前置**: `edge-case` `acceptance`

## 11. 证据 `evidence`
- **EN**: Evidence ｜ **归类**: 技术栈 · 测试 ｜ **来源**: 第4章·验收思维
- **tagline**: 验收只认证据不认口供：真实运行输出、测试结果、截图——「我觉得没问题」不算。
- **hook**: 「已完成并通过测试」这句话，值多少信任？
- **description**: 无论交付者是人还是 AI，「做完了」都只是陈述，不是事实。证据是能独立核验的东西：跑出来的日志、测试通过的输出、覆盖边界的用例列表。要证据不是不信任谁，是让质量可核验——AI 时代这条规矩更硬，因为 AI 的「已完成」说得比谁都流利。
- **✓ 建议**: 收货默认索要运行输出 ／ 关键功能留验收记录 ／ 「无证据=未完成」写进团队约定
- **✗ 避免**: 凭汇报语气判断完成度 ／ 证据只看结论不看过程 ／ 自己验收自己且不留痕
- **场景**: 「贴一下测试输出」的追问 ／ 上线评审的证据清单 ／ AI 汇报「全部通过」后的核验
- **前置**: `acceptance` `overconfidence`

## 12. 回归 `regression`
- **EN**: Regression ｜ **归类**: 技术栈 · 测试 ｜ **来源**: 第4章·验收思维
- **tagline**: 改 A 坏 B：新改动把原本好好的功能弄坏了——软件维护里最阴魂不散的事故来源。
- **hook**: 只是改了个按钮颜色，登录怎么就挂了？
- **description**: 代码之间有看不见的牵连，一处改动可能沿着依赖传到意想不到的角落。AI 大刀阔斧改代码时尤其高发：它不知道哪些行为是别处依赖的。对策是每次改动后重验老功能——自动化回归测试存在的全部理由。
- **✓ 建议**: 核心流程配自动化测试，每次改动全跑 ／ 验收新功能时顺带扫一遍老功能 ／ 大改动前先补测试再动手
- **✗ 避免**: 「就改了一行」不测直接上 ／ 手动回归靠记忆想到哪测到哪 ／ 测试挂了注释掉测试
- **场景**: 上线后老功能报障 ／ CI 里全量跑的测试套件 ／ 「这跟我改的没关系啊」的排查
- **前置**: `regression-test`
- **⚠**: VH 已有 `regression-test`（回归测试，手段），本条讲回归这个现象本身，挂它为前置。

## 13. 冻结期 `change-freeze`
- **EN**: Change Freeze ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第4章·验收思维
- **tagline**: 大促、发布会、假期前：停止一切非必要变更——稳定比新功能值钱的时刻。
- **hook**: 为什么电商团队双十一前两周什么都不敢上？
- **description**: 每次变更都带着风险，而有些时刻承受不起风险：流量洪峰、关键演示、没人值班的长假。冻结期就是给变更上闸：只放行紧急修复，其他一律排队。这不是保守，是对「变更是事故第一来源」这条统计规律的尊重。
- **✓ 建议**: 关键节点前设明确冻结窗口 ／ 冻结期例外走审批而不是口头 ／ 解冻后按优先级有序放行
- **✗ 避免**: 大促前夜「小改一下」 ／ 冻结期成为拖延借口（节后堆积成山） ／ 只冻代码不冻配置（配置改动同样能炸）
- **场景**: 双十一封网通知 ／ 假期前的上线截止线 ／ 冻结期紧急修复的审批流
- **前置**: `deploy`

## 14. 验收清单 `acceptance-checklist`
- **EN**: Acceptance Checklist ｜ **归类**: 技术栈 · 测试 ｜ **来源**: 第4章·验收思维
- **tagline**: 把验收从「凭感觉」变成「过清单」：功能、边界、失败路径、改动范围，逐项打勾。
- **hook**: 飞行员几千小时经验，起飞前为什么还要念检查单？
- **description**: 记忆靠不住，状态有起伏，清单不会。一份好的验收清单覆盖四类问题：spec 里的都做了吗、边界条件试过了吗、失败路径顺畅吗、diff 有没有越界。每次验收走同一份清单，质量就不再取决于当天的心情和咖啡因。
- **✓ 建议**: 按产品沉淀一份可复用清单并持续迭代 ／ 每条写成可勾选的具体动作 ／ 出过的事故转成新清单项
- **✗ 避免**: 清单空泛（「检查功能正常」等于没写） ／ 只建不用、用而不更 ／ 清单太长导致跳着打勾
- **场景**: 上线前的 checklist 走查 ／ 事故复盘补清单项 ／ 团队共享的验收模板
- **前置**: `acceptance` `spec`

## 15. 毫秒 / 微秒 / 纳秒 `time-scales`
- **EN**: ms / μs / ns ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第5章·数量级直觉
- **tagline**: 计算机世界的时间标尺：内存纳秒级、磁盘微秒级、网络毫秒级——差着上千倍。
- **hook**: 都说「很快」，内存和网络到底差多少？
- **description**: 1 毫秒 = 1000 微秒 = 100 万纳秒。读内存约百纳秒，读磁盘约百微秒，跨城网络来回几十毫秒——每跨一级慢上千倍。有了这把标尺，性能讨论才有单位：页面慢，先问慢在哪个量级，是代码（纳秒级的事）还是网络往返（毫秒级的事），方向立刻清楚。
- **✓ 建议**: 记住内存/磁盘/网络三个量级锚点 ／ 性能问题先定位量级再谈优化 ／ 讨论「快慢」时强制带单位
- **✗ 避免**: 用「感觉快/慢」代替测量 ／ 在纳秒级的代码里抠性能、放过毫秒级的网络往返 ／ 把不同量级的耗时混在一起比较
