## 1. 链路追踪 `tracing`
- **EN**: Tracing ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: observability
- **tagline**: 给每个请求发一张全程车票：经过哪站、每站停了多久，全记在票上——慢在哪一跳一眼看到。
- **hook**: 接口慢了三秒，是数据库慢还是第三方慢？
- **description**: 链路追踪给每个请求发一个唯一 ID，随它流经的每个服务一路传递，记下每一跳的耗时。一次下单可能穿过网关、订单、库存、支付四个环节，日志各写各的，只有 trace 能把它们拼成一条完整时间线，慢在哪一跳一目了然。排查问题时把 trace 贴给 AI，比贴十段互不相干的日志有用得多——前提是搭系统时就把它接上。
- **✓ 建议**: 让 AI 搭服务时把 trace ID 透传 ／ 排查慢请求先看链路瀑布图 ／ 统一让跨服务日志带上 trace ID
- **✗ 避免**: 在每个服务里翻日志人肉拼线索 ／ 只看总耗时不看分段耗时 ／ 等出了事故才想起来接入（来不及）
- **场景**: 下单慢三秒的排查 ／ 微服务事故复盘 ／ 性能优化立项之前
- **前置**: `log`

## 2. SLO / 可用性 `slo`
- **EN**: SLO / Availability ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: observability
- **tagline**: 服务质量的承诺线：99.9% 听着近乎完美——换算成宕机时间，一年是 8.7 小时。
- **hook**: 一年宕机 8.7 小时，你的用户能忍吗？
- **description**: SLO 是给服务质量画的承诺线，通常用几个 9 表示。99.9% 换算过来是一年允许宕机约 8.7 小时，99.99% 才缩到 52 分钟——而每多一个 9，架构复杂度和成本都会陡增。给自己产品定线前先想清楚：用户要的是四个 9，还是三个 9 加一份诚恳的故障公告；选云服务和 AI API 时，也翻翻对方承诺了几个 9、宕机赔什么。
- **✓ 建议**: 按业务算清自己到底需要几个 9 ／ 选服务商先查 SLA 和赔偿条款 ／ 备好状态页和故障公告模板
- **✗ 避免**: 张口承诺 100% 可用（物理上不存在） ／ 盲目堆 9 把预算烧在过度架构上 ／ 定了 SLO 却从来不度量不复盘
- **场景**: 云服务商 SLA 条款页 ／ 年度宕机时长复盘 ／ 企业客户合同谈判
- **前置**: `metrics`

## 3. IaaS `iaas`
- **EN**: Infrastructure as a Service ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: cloudcost
- **tagline**: 租毛坯房自己装修：云只给裸机和网络，系统、环境、补丁全归你——自由最大，负担也最大。
- **hook**: 买了台云服务器，半夜的安全补丁谁来打？
- **description**: IaaS 是云的最底层：租到的是虚拟机、硬盘和网络，相当于拿了一间毛坯房的钥匙。装系统、配环境、开防火墙、打补丁、做扩容，全部自己来——自由度拉满，运维负担也拉满。AI 能替你写运维脚本，但半夜宕机、被入侵挖矿这些事故，最后扛着的还是你；没有专职运维之前，产品人慎选这条路。
- **✓ 建议**: 需要特殊环境或极致成本再选它 ／ 让 AI 写运维脚本也自己留快照备份 ／ 没有运维人手时优先考虑 PaaS
- **✗ 避免**: 为了「听起来专业」上手就租裸机 ／ 装完环境从此不打安全补丁 ／ root 用弱密码直接裸奔公网
- **场景**: AWS EC2 购买页面 ／ 自建数据库的选型讨论 ／ 服务器被挖矿的复盘
- **前置**: `server`

## 4. PaaS / 托管平台 `paas`
- **EN**: Platform as a Service ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: cloudcost
- **tagline**: 精装公寓拎包入住：你只管代码，机器、扩容、证书平台全包——vibe coder 的默认选择。
- **hook**: 一行运维没做，网站怎么就上线了？
- **description**: PaaS 把服务器细节全收进平台：你推一次代码，Vercel、Railway 这类平台自动完成构建、部署、扩容、续证书。AI 生成的项目大多天然适配这条路，从写完到上线能压进十分钟——这正是它成为 vibe coder 默认选择的原因。代价有两个：按用量计费在量大后可能比裸机贵，深度绑定平台后迁移也有成本；但验证期这笔账几乎总是划算的。
- **✓ 建议**: 验证期默认选 PaaS 省下运维时间 ／ 部署当天顺手配好预算报警 ／ 读一遍计费规则再选套餐
- **✗ 避免**: 项目还没用户就纠结平台贵不贵 ／ 把 API 密钥写死在代码里推上去 ／ 量大了还硬扛天价账单不评估迁移
- **场景**: Vercel 一键部署 ／ AI 生成项目的上线首选 ／ 免费额度用超的账单
- **前置**: `deploy`

## 5. 带宽 / 流量费 `egress`
- **EN**: Bandwidth / Egress ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: cloudcost
- **tagline**: 数据出云要交过路费：进来免费、出去按 GB 计——账单刺客的常驻位。
- **hook**: 一个 1GB 的视频被看一万次，等于多少账单？
- **description**: 云厂商的通行规则是「数据进来免费，出去按量收费」——用户每下载一个文件、看一段视频，都在给你的账单加码。大文件站、图床、被爬虫盯上的接口是重灾区：一个 1GB 视频被刷一万次，流出的就是 10TB，够一夜刷出四位数账单。上线任何下载类功能前，先按「如果它火了」算一遍流量账，再把 CDN、防盗链和限流配齐。
- **✓ 建议**: 大文件和视频走 CDN 或对象存储 ／ 给下载接口加限流和防盗链 ／ 按「爆款流量」预演一遍账单
- **✗ 避免**: 以为流量和存储一样便宜 ／ 原图原视频直接对公网裸奔 ／ 被爬崩了才去翻计费文档
- **场景**: 月底账单里最大一项 ／ 视频功能的成本测算 ／ 被恶意刷流量的事故
- **前置**: `server`

## 6. 预算报警 `budget-alert`
- **EN**: Budget Alert ｜ **归类**: backend · 上线与排错 ｜ **来源回路**: cloudcost
- **tagline**: 给云账单装保险丝：花费过线自动喊人——五分钟配置，救你于一觉醒来的天价账单。
- **hook**: 睡前一切正常，醒来账单四位数——中间发生了什么？
- **description**: 预算报警是云平台自带的保险丝：设一个金额阈值，花费冲线就自动发邮件短信，有的还能直接停服务。死循环调用、被刷的接口、忘关的测试实例，都在你睡着时烧钱——尤其 AI API 按 token 计费，一段失控的循环一晚上就能烧穿信用卡。这是所有云配置里性价比最高的五分钟，注册当天就该做完。
- **✓ 建议**: 开通任何云服务当天就设报警 ／ 给 AI API 单独设用量硬上限 ／ 分级设阈值：50% 提醒、100% 告警
- **✗ 避免**: 想着「我用量小不至于」就跳过 ／ 只设提醒不设自动断供 ／ 报警邮件进垃圾箱从没人看
- **场景**: 新云账号的第一项配置 ／ AI API 用量上限设置 ／ 天价账单事故的复盘
- **前置**: `monitoring`

## 7. 并发 `concurrency`
- **EN**: Concurrency ｜ **归类**: backend · 后端开发 ｜ **来源回路**: concurrency
- **tagline**: 多个请求同一瞬间挤进门：你一个人测一百遍都没事的代码，一百人同时用就翻车。
- **hook**: 自己测一百遍都正常，一百人同时用就崩？
- **description**: 并发是多个请求在同一瞬间到达——不是排队进门，而是一起挤进门。单人测试永远是串行的，所以并发 bug 在开发环境几乎必然漏网：两个人同时注册同一个用户名、一百个人同时抢最后一件库存，都是自己点一百遍也复现不了的问题。AI 写代码同样默认串行思维，凡是带「抢」和「同时」的场景，要主动告诉它预期并发量，再用压测验证。
- **✓ 建议**: 压测抢购、计数类关键功能 ／ 提示 AI「这里会有并发」再生成 ／ 用数据库唯一约束兜底
- **✗ 避免**: 拿「我测过没问题」下结论 ／ 先读后写中间不加任何保护 ／ 把并发问题留到用户多了再说
- **场景**: 秒杀活动上线前评审 ／ 重复注册同名用户的 bug ／ 压测报告的请求曲线
- **前置**: （无）

## 8. 竞态条件 `race-condition`
- **EN**: Race Condition ｜ **归类**: backend · 后端开发 ｜ **来源回路**: concurrency
- **tagline**: 两个操作抢同一条数据，结果看谁跑得快：库存明明剩 1 件，却卖出去 2 件。
- **hook**: 库存只剩 1 件，怎么两个人都买到了？
- **description**: 竞态条件是并发的典型病灶：两个操作都先读数据、再写回去，中间没有任何隔离。抢最后一件库存时，A 和 B 同时读到「还剩 1」，各自判断能买、各自扣一次——库存变成 -1，超卖发生。它的阴险在于难复现：一千次里可能只出一次，测试全绿照样上线翻车。防法是把「读—判断—写」压成一个不可分割的动作，交给数据库或锁来保证。
- **✓ 建议**: 改「先查再改」为原子操作 ／ 让 AI 自查读与写之间的间隙 ／ 用唯一索引挡住重复写入
- **✗ 避免**: 拿「概率很低」当护身符 ／ 复现不出来就当它不存在 ／ 在前端做判断防超卖（防不住）
- **场景**: 电商超卖事故分析 ／ 优惠券被重复领取 ／ 余额扣成负数的工单
- **前置**: `concurrency`

## 9. 锁 `lock`
- **EN**: Lock ｜ **归类**: backend · 后端开发 ｜ **来源回路**: concurrency
- **tagline**: 关键区门口的独木桥：同一时刻只放一个操作进去——安全了，但后面全在排队。
- **hook**: 加了锁不超卖了，怎么下单也变慢了？
- **description**: 锁的逻辑很朴素：进关键区先领牌子，牌子只有一块，别人来了就等。它是治竞态的直接手段——扣库存前上锁、改完释放，超卖立刻消失。但锁的本质是把并行改回串行：锁的范围越大、握得越久，队伍排得越长；异常时忘了释放，整个系统还会死等。让 AI 加锁时盯两件事：锁的粒度尽量小，出错时必须释放。
- **✓ 建议**: 把锁的范围压到最小几行 ／ 给锁设超时避免死等 ／ 能用原子操作就不上锁
- **✗ 避免**: 一把大锁包住整个函数图省事 ／ 异常分支里忘了释放锁 ／ 到处加锁把系统锁成单车道
- **场景**: 扣库存代码的评审 ／ 死锁导致的服务卡死 ／ 锁还是原子操作的讨论
- **前置**: `race-condition`

## 10. 原子操作 `atomic`
- **EN**: Atomic Operation ｜ **归类**: backend · 后端开发 ｜ **来源回路**: concurrency
- **tagline**: 要么全做完，要么像没发生过：中间状态谁也看不见——扣库存的正确姿势。
- **hook**: 不加锁也能防超卖，靠的是什么？
- **description**: 原子操作把「读—算—写」压成一步，执行期间不存在能被插队的中间态。扣库存的正确写法不是「查出来减一再存回去」，而是一句「库存减一，但仅当库存大于零」——数据库一步完成，一万个并发也插不进缝。它比锁更轻：不排长队、不怕忘释放。验收 AI 写的库存、余额、计数逻辑时，先问一句「这步是原子的吗」。
- **✓ 建议**: 用数据库原子语句做扣减 ／ 用事务包住转账类多步操作 ／ 验收时追问「中间态可见吗」
- **✗ 避免**: 查出来在代码里算完再写回 ／ 以为代码只有一行就自动原子 ／ 把原子性寄托在用户手速上
- **场景**: 库存扣减的标准写法 ／ 计数器少计数的排查 ／ 转账事务的代码评审
- **前置**: `race-condition`

## 11. O(1) 常数 `constant-time`
- **EN**: O(1) Constant Time ｜ **归类**: backend · 后端开发 ｜ **来源回路**: complexity
- **tagline**: 数据翻一万倍，耗时纹丝不动：报着门牌号直接敲门，不用挨家挨户找。
- **hook**: 一亿条数据里取一条，凭什么毫秒级？
- **description**: O(1) 是性能的天花板：数据量再怎么涨，这一步操作的耗时都不变。按主键取一条记录、哈希表里按 key 找值，都是报着门牌号直接敲门——数据从一万涨到一亿，速度几乎原地不动。设计高频操作时尽量给它铺一条 O(1) 路径：查询带上主键或唯一键，别让数据库挨家挨户翻。这也是理解「索引为什么快」的起点。
- **✓ 建议**: 高频查询走主键或唯一键 ／ 频繁按 key 取值用哈希结构 ／ 压测验证耗时不随数据量涨
- **✗ 避免**: 数据少时用遍历没事就一直拖 ／ 把 O(1) 当免费午餐无限堆内存 ／ 分不清「取一条」和「翻一遍」
- **场景**: 按 ID 查订单详情 ／ 缓存命中的耗时曲线 ／ 性能优化方案对比
- **前置**: （无）

## 12. O(log n) 对数 `logarithmic-time`
- **EN**: O(log n) Logarithmic ｜ **归类**: backend · 后端开发 ｜ **来源回路**: complexity
- **tagline**: 数据翻倍只多走一步：一亿条里找一条，二十几次比较就够——索引的魔法。
- **hook**: 猜 1 到 100 的数字，最多几次能猜中？
- **description**: O(log n) 的秘诀是每一步排除一半：猜 1 到 100 的数，从 50 开始问「大了还是小了」，7 次以内必中。二分查找、数据库索引都是这个原理——一亿条数据只要二十几步，翻倍到两亿也只多一步。给常用查询字段建索引，就是花一点写入和存储的代价，把全表扫描换成对数级查找。查询一慢先查有没有索引，这一招能解决大半问题。
- **✓ 建议**: 给常用查询和排序字段建索引 ／ 查询慢先看执行计划走没走索引 ／ 有序数据用二分代替遍历
- **✗ 避免**: 给每个字段无脑建索引（拖慢写入） ／ 模糊搜索硬套索引还奇怪没生效 ／ 数据没排序就直接上二分
- **场景**: 慢查询优化第一步 ／ 「加个索引就好了」的时刻 ／ 数据库执行计划分析
- **前置**: `constant-time`

## 13. O(n) 线性 `linear-time`
- **EN**: O(n) Linear ｜ **归类**: backend · 后端开发 ｜ **来源回路**: complexity
- **tagline**: 数据翻倍，耗时跟着翻倍：从头到尾过一遍——一万条起，你开始有感觉。
- **hook**: 列表一万条时，页面打开慢了半拍，巧合吗？
- **description**: O(n) 是把数据从头到尾过一遍：数量涨多少，耗时就涨多少。它本身不是错——汇总、导出这类活天生要遍历。问题出在位置：一次遍历放在偶发的后台任务里无所谓，放在每次打开页面都跑的路径上，一万条就是可感的卡顿，百万条就是事故。AI 生成的代码偏爱「全量查出来再在内存里处理」，看到列表功能，本能地问一句「数据涨十倍会怎样」。
- **✓ 建议**: 列表页一律分页或懒加载 ／ 把汇总统计挪到后台或预计算 ／ 用十倍数据量做一次压测
- **✗ 避免**: 全量查出来在内存里慢慢过滤 ／ 拿一百条测试数据下性能结论 ／ 在循环里逐条查数据库
- **场景**: 列表页越用越慢的反馈 ／ 全量导出拖垮服务 ／ 评审里的全表查询
- **前置**: `constant-time`

## 14. O(n²) 平方 `quadratic-time`
- **EN**: O(n²) Quadratic ｜ **归类**: backend · 后端开发 ｜ **来源回路**: complexity
- **tagline**: 数据翻倍，耗时四倍：双重循环两两比较——一万条就是一亿次操作，直接卡死。
- **hook**: 一万条数据两两比一遍，是多少次运算？
- **description**: O(n²) 通常长这样：循环里再套一层循环，让每条数据和其余每条都见一面。一百条时是一万次操作，眨眼完成；一万条时就是一亿次，页面直接冻住——数据翻倍，耗时四倍，比你的用户增长快得多。查重、找相似、配对撮合是高发区，AI 图省事时也特别爱写双重循环：代码能跑、测试能过，一上量原形毕露。见到嵌套循环，先问一句数据量上限是多少。
- **✓ 建议**: 见到嵌套循环先问 n 有多大 ／ 查重改用哈希集合一遍过 ／ 让 AI 重写时明说数据量级
- **✗ 避免**: 拿「测试数据跑得快」当性能结论 ／ 在循环里再调一次查询或接口 ／ 指望加服务器硬抗平方级增长
- **场景**: 查重功能一上量就卡 ／ 双重 for 循环的评审 ／ 「昨天还好好的」性能悬案
- **前置**: `linear-time`
