## 1. 源代码 `source-code`
- **EN**: Source Code ｜ **归类**: 后端 · 后端开发 ｜ **来源**: 第0章·解剖一次 vibe coding
- **tagline**: 人和 AI 写下的指令文本文件，描述程序该做什么，但自身不会运行。
- **hook**: AI 生成的那一堆 .ts、.py 文件到底是什么？
- **description**: 项目里所有以代码后缀结尾的文件都是源代码。它是项目的核心资产：依赖可以重装、产物可以重建，源代码丢了就什么都没了。让它"动起来"需要经过运行或构建。
- **✓ 建议**: 把源代码当唯一核心资产对待，纳入版本控制 ／ 让 AI 改动后先看它改了哪些源码文件 ／ 提需求时分清改文案还是改逻辑，量级完全不同
- **✗ 避免**: 把源代码和构建产物混在一起手改产物 ／ 只保存打包结果不保存源码 ／ 项目出问题直接删目录重来（源码历史一起丢）
- **场景**: 项目文件夹里的 src 目录 ／ GitHub 仓库文件列表 ／ AI 改动后的 diff 视图
- **前置**: 无

## 2. 依赖 `dependency`
- **EN**: Dependency ｜ **归类**: 后端 · 后端开发 ｜ **来源**: 第0章·解剖一次 vibe coding
- **tagline**: 项目用到的别人写好的代码包，按清单安装、可随时重装再生。
- **hook**: node_modules 里几万个文件是我写的吗？要备份吗？
- **description**: 现代软件站在几百个开源包的肩膀上组装。依赖清单（如 package.json）记录"进了什么货"；安装命令按清单把包拉到本地。依赖目录体积巨大但完全可再生，所以从不进版本库。
- **✓ 建议**: 只提交依赖清单，不提交依赖目录 ／ 拉到新项目先跑安装命令再启动 ／ 升级依赖后跑一遍测试确认没被破坏
- **✗ 避免**: 手改 node_modules 里的代码（重装即丢） ／ 把依赖目录发给别人当备份 ／ 无清单地散装复制代码包
- **场景**: npm install 的进度条 ／ package.json 的 dependencies 段 ／ CI 里的装依赖步骤
- **前置**: `npm`

## 3. 运行 / 进程 `process`
- **EN**: Run / Process ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第0章·解剖一次 vibe coding
- **tagline**: 程序被读进内存执行后形成的"活着的实例"；窗口关了、机器重启，进程就没了。
- **hook**: 为什么关掉终端，页面就打不开了？
- **description**: 源代码是乐谱，进程是演奏。`npm run dev` 之后一直滚动的那个东西就是活着的进程，它持续守着端口响应请求。进程内的临时数据重启即丢——这解释了"在我电脑上是好的"与"重启就没了"两大日常谜团。
- **✓ 建议**: 分清"改了代码"和"重启了进程"是两件事 ／ 排错先确认进程还活着、听的是哪个端口 ／ 需要常驻的服务交给服务器托管而不是自己的终端窗口
- **✗ 避免**: 关终端后疑惑网站怎么挂了 ／ 把重要状态只存进程内存 ／ 同端口起两个进程互相打架
- **场景**: 终端里滚动的 dev server 日志 ／ 活动监视器的进程列表 ／ 部署平台的重启按钮
- **前置**: `terminal`

## 4. 配置文件 `config-file`
- **EN**: Config File ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第0章·解剖一次 vibe coding
- **tagline**: 用小文件声明程序的行为参数：小而关键，改它不用改代码。
- **hook**: 项目根目录那一排点开头的小文件是干嘛的？
- **description**: 端口、路径、开关、密钥引用……都住在配置文件里。它们体量最小、影响最大：一行配置写错可以让整个项目起不来。密钥类配置（.env）绝不进版本库。
- **✓ 建议**: 改行为先想"是不是配置就能解决" ／ .env 进 .gitignore、只提交 .env.example ／ 配置变更也走版本记录，出问题能回溯
- **✗ 避免**: 把真实密钥写进任何会提交的文件 ／ 手改线上配置不留记录 ／ 把业务逻辑塞进配置里
- **场景**: 项目根目录的 .env / next.config / tsconfig ／ 部署平台的环境变量面板
- **前置**: `env-var`

## 5. localhost `localhost`
- **EN**: localhost / 127.0.0.1 ｜ **归类**: 后端 · 网络与地址 ｜ **来源**: 第0章·本地与服务器
- **tagline**: "我自己这台机器"的代号；访问它请求不出电脑，所以断网能开、别人永远打不开。
- **hook**: 为什么我发 localhost:3000 给别人，他打不开？
- **description**: localhost 指向本机回环地址。开发时页面跑在自己电脑上，用 localhost+端口访问；这个地址对世界上任何其他设备都无意义。想让别人看到，需要部署到有公网地址的服务器。
- **✓ 建议**: 演示给别人前先部署或开隧道 ／ 分清 localhost 页面与线上页面是两个世界 ／ 排错时先确认访问的是本地还是线上
- **✗ 避免**: 把 localhost 链接发给客户 ／ 在本地改完就以为线上也变了 ／ 用 localhost 地址配置给真实用户用的服务
- **场景**: 浏览器地址栏 localhost:3000 ／ dev server 启动提示 ／ 手机连不上电脑页面的时刻
- **前置**: `port`

## 6. 服务器 `server`
- **EN**: Server ｜ **归类**: 后端 · 网络与地址 ｜ **来源**: 第0章·本地与服务器
- **tagline**: 一台不关机、有公网地址、专门守着响应请求的电脑——没有任何魔法。
- **hook**: 所谓"上云"到底是把代码放到哪里去了？
- **description**: 你租的云服务器，本质是别人机房里一台替你 24 小时开机的电脑。产品要让别人随时打开，就得跑在这种机器上。本地是草稿，服务器是正式演出场地。
- **✓ 建议**: 记住"部署 = 把进程搬到不关机的机器上" ／ 关心它在哪个地区、影响用户延迟 ／ 出问题分清是代码错还是服务器环境错
- **✗ 避免**: 以为云是某种非实体的魔法 ／ 用自己的笔记本当长期服务器 ／ 忘了服务器也会满、也要维护
- **场景**: 云厂商控制台 ／ 部署平台的机器规格选择 ／ "服务器挂了"的报警
- **前置**: `localhost`

## 7. IP 地址 `ip-address`
- **EN**: IP Address ｜ **归类**: 后端 · 网络与地址 ｜ **来源**: 第0章·本地与服务器
- **tagline**: 网络世界的门牌号，每台联网设备一个；公网 IP 全球可达，内网 IP 只在局域网有效。
- **hook**: 域名背后那串数字是什么？
- **description**: 请求最终都要送到某个 IP。服务器有公网 IP，所以全世界都能敲它的门；家里的笔记本通常只有内网 IP（192.168.x.x），出了家门无人认识。域名解析的终点就是 IP。
- **✓ 建议**: 排查"打不开"时先分清公网还是内网地址 ／ 理解域名 → IP → 机器这条链路 ／ 服务器换 IP 后记得更新域名指向
- **✗ 避免**: 把内网 IP 发给外部用户 ／ 把 IP 硬编码进代码里 ／ 混淆"同一 WiFi 可访问"与"全网可访问"
- **场景**: ping 命令的输出 ／ 域名解析设置页 ／ 服务器控制台的公网 IP 栏
- **前置**: `dns`

## 8. 部署 `deploy`
- **EN**: Deploy ｜ **归类**: 后端 · 上线与排错 ｜ **来源**: 第0章·本地与服务器
- **tagline**: 把代码从"我电脑"搬到服务器并运行起来的全过程；完成标志是别人用域名能打开。
- **hook**: "上线"在工程上到底包含哪几步？
- **description**: 部署不只是拷文件：装依赖、重启进程、配置域名与证书，每一步都可能出错。"我电脑上是好的"之所以是名梗，就因为线上环境和本地环境是两套世界。
- **✓ 建议**: 每次部署后用真实域名亲手点一遍关键流程 ／ 保留上一版可回滚 ／ 部署与配置变更留记录
- **✗ 避免**: 周五晚上部署然后关电脑 ／ 部署完不验证就宣布上线 ／ 直接在服务器上手改代码
- **场景**: 部署平台的 build 日志 ／ 上线后第一次打开自己的域名 ／ 回滚按钮
- **前置**: `server` ／ `domain`
- **备注**: VH 已有 `deployment`（技术栈视角）；本条为课程"从本地到线上"视角。审校时二选一：并存或合并。

## 9. 渲染 `render`
- **EN**: Render ｜ **归类**: 前端 · 网页基础 ｜ **来源**: 第0章·从输入网址到看到页面
- **tagline**: 浏览器把收到的代码变成你看见的像素的过程。
- **hook**: 数据都到了，为什么页面还白着？
- **description**: 请求带回来的只是文本；浏览器要解析结构、套样式、执行脚本，才把界面画出来。渲染卡住的典型表现：白屏、闪烁、点了没反应。前端性能话题大半在讲怎么让渲染更早更稳。
- **✓ 建议**: 把"数据到了"和"画面出来了"当两个阶段排查 ／ 关注首屏渲染要等多少资源 ／ 大列表用分页或虚拟化减轻渲染
- **✗ 避免**: 一次渲染上万条数据 ／ 阻塞渲染的巨型脚本放页面头部 ／ 把渲染问题当网络问题修
- **场景**: 白屏等待的瞬间 ／ DevTools 的性能面板 ／ 骨架屏出现又消失
- **前置**: `dom`

## 10. 首屏时间 `first-paint`
- **EN**: First Paint / LCP ｜ **归类**: 前端 · 网页基础 ｜ **来源**: 第0章·从输入网址到看到页面
- **tagline**: 从输入网址到看见主要内容的耗时；用户对"快不快"的判断几乎全在这几百毫秒。
- **hook**: 那 0.3 秒里到底发生了什么？
- **description**: DNS、连接、响应、渲染，每一站都在吃首屏预算。LCP（最大内容绘制）是常用口径：主要内容多久出现。产品讨论"加载慢"时，先看首屏指标，再谈体感。
- **✓ 建议**: 给产品定一个首屏预算并盯住它 ／ 图片压缩与懒加载优先做 ／ 用真实用户数据而不是本机体感评估
- **✗ 避免**: 首页塞满未压缩大图 ／ 把所有脚本同步加载 ／ 拿公司内网的速度代表用户网络
- **场景**: Lighthouse 报告的 LCP 一栏 ／ 用户抱怨"打开好慢" ／ 性能监控面板
- **前置**: `render`

## 11. 请求 / 响应 `request-response`
- **EN**: Request / Response ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第1章·前端、后端与数据库
- **tagline**: 前后端对话的基本回合：一问一答，一来一回。
- **hook**: 点一下"下单"，请求走过了哪几站？
- **description**: 前端把输入打包成请求发给后端；后端验证、执行、写库，再把结果作为响应原路送回；前端拿到响应更新画面。产品里每个可感知的操作背后都是若干个这样的回合。
- **✓ 建议**: 排错先看请求发没发出去、响应回的是什么 ／ 给每个请求想清楚失败分支 ／ 用 DevTools 网络面板当第一现场
- **✗ 避免**: 只看界面不看网络面板就下结论 ／ 假设请求一定成功 ／ 一个操作静默发出大量重复请求
- **场景**: DevTools Network 里的一行 ／ "转圈圈"的等待态 ／ 接口超时报错
- **前置**: `http`

## 12. 契约 `contract`
- **EN**: Contract ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第1章·API：系统间的契约
- **tagline**: 接口双方事先写明的约定：地址与动作、输入、成功输出、失败输出。
- **hook**: 你写的 PRD，其实就是契约的产品版本。
- **description**: 契约的专业度差距几乎全体现在失败分支的完整度上：没库存怎么办？未登录怎么办？重复提交怎么办？把这些写清楚，AI 和协作者才不会各自即兴发挥。多 Agent 并行开发时，先定契约是唯一能让它们互不打架的方法。
- **✓ 建议**: 写 PRD 时给关键流程补一段"失败了会怎样" ／ 字段名、单位、边界一次写明 ／ 契约变更走文档和版本
- **✗ 避免**: 只写晴天路径 ／ 口头约定接口 ／ 改字段名不通知消费方
- **场景**: 接口文档评审 ／ 前后端联调对不上的现场 ／ 给 AI 的功能说明
- **前置**: `api`

## 13. 幂等 `idempotent`
- **EN**: Idempotent ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第1章·API：系统间的契约
- **tagline**: 同一个操作执行一次和执行多次，结果一样——网络世界的防重复保险。
- **hook**: 用户手抖点了三次"支付"，会扣三次钱吗？
- **description**: 网络会超时、用户会重试，同一请求到达多次是常态而不是意外。幂等设计让"多次到达"无害：同一订单号重复提交只生效一次。支付、下单、扣库存这类接口不幂等，就是在等事故。
- **✓ 建议**: 写敏感操作的 PRD 时问一句"重复提交怎么处理" ／ 用唯一业务号做去重 ／ 超时后的重试策略与幂等配套设计
- **✗ 避免**: 假设每个请求只会到达一次 ／ 靠前端按钮置灰当唯一防线 ／ 重试逻辑叠加在不幂等的接口上
- **场景**: 支付确认页的防重复提示 ／ 订单去重逻辑评审 ／ 超时重试后的对账
- **前置**: `contract`
- **⚠ 高频审校点**: 这是全批最"工程"的一条，表述请重点过目。

## 14. 状态码 `status-code`
- **EN**: Status Code ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第1章·API：系统间的契约
- **tagline**: 响应自带的三位数结果标签：2xx 成功，4xx 请求方的错，5xx 服务方的错。
- **hook**: 4xx 怪你，5xx 怪我——一句话看懂报错该找谁。
- **description**: 状态码是排错的第一分流：401 没登录、403 没权限、404 找不到、409 冲突、500 服务端炸了。产品经理能读状态码，就能在群里第一时间判断该 at 前端还是后端。
- **✓ 建议**: 报错先看状态码再看文案 ／ 契约里为每类失败指定状态码 ／ 4xx 给用户可读提示、5xx 触发报警
- **✗ 避免**: 所有错误一律返回 200+错误文案 ／ 把 4xx 当服务端事故处理 ／ 用户可见页面直接裸露 500
- **场景**: DevTools 里标红的一行 ／ 接口文档的失败分支表 ／ 报警群里的 5xx 曲线
- **前置**: `http`

## 15. 向后兼容 `backward-compatible`
- **EN**: Backward Compatible ｜ **归类**: 后端 · 接口与数据 ｜ **来源**: 第1章·API：系统间的契约
- **tagline**: 接口升级后，老的调用方式仍然能用——改动不打碎既有使用者。
- **hook**: 后端改个字段名，为什么别人的 App 全崩了？
- **description**: 契约一旦有消费方，改动就要向后兼容：加字段可以，删改字段要先加新的、再废旧的、留过渡期。事故的根源常常不是技术，而是契约变更没有流程。
- **✓ 建议**: 改字段先加新再废旧 ／ 废弃字段标注期限并通知消费方 ／ 接口带版本号管理大改
- **✗ 避免**: 直接重命名/删除在用字段 ／ "反正是内部接口"心态 ／ 无版本无文档的静默变更
- **场景**: 接口 v1/v2 并存期 ／ 变更通知邮件 ／ 升级后老客户端的兼容测试
- **前置**: `contract`
